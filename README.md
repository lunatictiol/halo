# HALO — Grounded Knowledge Engine

[![ci](https://github.com/lunatictiol/halo/actions/workflows/ci.yml/badge.svg)](https://github.com/lunatictiol/halo/actions/workflows/ci.yml)

HALO answers questions over a hard corpus of 1,000 arXiv research papers. It **only answers when the papers support the answer**, cites where each claim comes from (paper, section, page), and **abstains** when the corpus can't back an answer up. It retrieves with hybrid search, reranks, checks whether the evidence actually answers the question, rewrites the query and retries when it doesn't, and verifies its own citations before it speaks.

It is also an evaluation project. Every stage was added only after a harness measured a before/after on a fixed question set, and every number below traces to a file in [`results/`](results/).

> **Every number in this README comes from a file in [`results/`](results/)**: the tables in [Results](#results) are generated by `uv run python -m eval.report.readme`, and the analysis quotes [`results/m6_report.md`](results/m6_report.md), [`results/m9_chunking.md`](results/m9_chunking.md), [`results/m10_stream_latency.json`](results/m10_stream_latency.json) and [`results/m11_docker.json`](results/m11_docker.json). Nothing is quoted from memory.

## What it does

Given a question, HALO:

1. **Retrieves** candidate passages with hybrid search: dense embeddings and BM25 keyword search, fused with Reciprocal Rank Fusion.
2. **Reranks** the candidates with a cross-encoder.
3. **Grades** whether the evidence actually answers the question.
4. **Corrects itself**: if the evidence is insufficient, it rewrites the query and retrieves again (at most 2 retries).
5. **Answers with citations** (paper, section, page), or **abstains** with a reason when the evidence never becomes sufficient.
6. **Verifies** that every cited passage supports the sentence that cites it, and drops the sentences that fail.

```mermaid
flowchart LR
    Q[Question] --> R[Retrieve<br/>dense + BM25 → RRF]
    R --> RR[Rerank<br/>cross-encoder]
    RR --> G{Grade<br/>evidence sufficient?}
    G -- yes --> A[Answer with citations]
    G -- "no, retries left" --> W[Rewrite query] --> R
    G -- "no, retries exhausted" --> X[Abstain with reason]
    A --> V[Citation check]
```

Most RAG demos show that retrieval *works*. HALO is built to show that it is *measured*: the evaluation harness came before any optimization, and each stage (baseline → hybrid → rerank → corrective loop → grounded citations) had to show a measured improvement on the same fixed question set. Abstention is a first-class behavior, tested on questions whose source papers are deliberately never indexed.

## At a glance

| | |

| Corpus | 1,000 arXiv papers; 980 indexed (20 held out for the abstention test), 60,153 chunks ([`m6_index.txt`](results/m6_index.txt)) |

### System overview

HALO is one Python process (FastAPI + a LangGraph state graph) that owns two local stores, an embedded Qdrant index and an in-memory BM25 index, and talks to one external service, Ollama, for every language-model call.

```mermaid
flowchart TB

        http["HTTP clients<br/>POST /query"]
        cli["CLI<br/>python -m halo.cli"]
    end
    subgraph app["HALO app: one Python process"]
        api["API layer (FastAPI)<br/>/query · /query/stream · /ui/* · /health · /ready"]
        loop["Corrective loop (LangGraph)<br/>retrieve → rerank → grade → generate / rewrite / abstain → verify"]
        retr["Hybrid retriever<br/>dense + BM25 → RRF"]
        rr["Cross-encoder reranker<br/>bge-reranker-v2-m3"]
        qd[("Qdrant, embedded<br/>chunk vectors + metadata")]
        bm[("BM25 index<br/>built in memory at startup")]
        llmc["LLM client<br/>chat · schema-constrained classify"]
    end
    ol["Ollama<br/>qwen3:8b · nomic-embed-text"]

    http --> api
    cli --> loop
    api --> loop
```

### Offline indexing

Indexing runs once (`scripts/download_data.py`, then `scripts/ingest.py`) and writes everything the app needs into `data/`.

```mermaid
flowchart LR
    dl["download_data.py<br/>HF metadata + corpus JSON + arXiv PDFs"] --> data[("data/<br/>hf/ · pdfs/")]
    data --> pdf["PDF reader<br/>PyMuPDF text blocks + page numbers"]
    data --> sec["Vectara sections<br/>corpus/ID.json"]
    pdf --> map["Block → section mapping<br/>5-gram overlap, min_match 0.3"]
    sec --> map
    map --> chunk["Section-aware chunker<br/>300 words, 50 overlap,<br/>never crosses a section"]
    chunk --> emb["Embed<br/>nomic-embed-text, batches of 64"]
    emb --> up["Qdrant upsert<br/>delete-then-upsert per paper,<br/>deterministic point ids"]
```

- **Why map blocks to sections instead of detecting headings.** The relevance labels (qrels) point at Vectara's own section IDs, which do not follow the PDF's headings. Each PDF text block takes the section that contains most of its word 5-grams; a block that matches no section well (headers, references, math-only blocks; below `min_match = 0.3`) inherits the previous block's section (D12, D13).
- **Chunks never cross a section.** A chunk is a 300-word window (50-word overlap) over consecutive blocks of one section, so a hit is attributable to exactly one (paper, section) pair, the unit the labels score (D14). Fixed-size windows that ignore sections lost 0.18 R@5 in the M9 benchmark ([below](#chunking-benchmark-m9)).
- **Every chunk carries its provenance:** `paper_id`, `chunk_idx`, `section_id`, `section_title`, `page`, `page_end` and `text`. All 60,153 chunks of the full index have a paper ID, section ID and page ([`m6_index.txt`](results/m6_index.txt)); this is what makes a citation resolvable.
- **Idempotent.** Point IDs are deterministic (`uuid5` of paper and chunk index) and each paper is deleted then re-upserted, so re-running ingestion leaves the same chunk count, no duplicates and no stale points from a changed chunker.
- **BM25 is not stored.** It is rebuilt in memory from the Qdrant payloads when the app starts, so it can never drift from the dense index (D21).
- Embeddings use nomic-embed-text's task prefixes (`search_document: ` for chunks, `search_query: ` for queries); omitting them degrades retrieval (D15).
- An optional contextual-enrichment step (an LLM writes 1–2 lines situating each chunk) exists and was measured; it is **not** used in the shipped index (D42, [below](#chunking-benchmark-m9)).

### The corrective loop

The query pipeline is an explicit LangGraph state graph, so every retry and abstention is a visible edge, not a hidden `while` loop.

```mermaid
flowchart TD
    Q([Question]) --> R["retrieve<br/>hybrid: dense + BM25 → RRF, 50 candidates"]
    R --> RR["rerank<br/>cross-encoder, keep the top 10"]
    RR --> G{"grade<br/>LLM: do the top 5 passages answer<br/>the original question?"}
    G -- sufficient --> GEN["generate<br/>top 5 passages, cites as P1 to P5"]
    G -- "insufficient, attempts ≤ 2" --> W["rewrite<br/>new query from the grader's reason<br/>and every query already tried"]
    W --> R
    G -- "insufficient, attempts > 2" --> AB["abstain<br/>INSUFFICIENT_EVIDENCE + the grader's reason"]
    GEN --> V["verify<br/>per-sentence grounding check"]
    V -- "at least one sentence supported" --> OUT([Answer with citations])
    V -- "none supported, or the model itself<br/>replied INSUFFICIENT_EVIDENCE" --> AB2["abstain<br/>generator or grounding-check reason"]
```

| Node | What it does |
|---|---|
| `retrieve` | Runs the configured first-stage method (`hybrid`) on the *current* query, records it in `tried`, increments `attempts` |
| `rerank` | Scores the fused candidates against the current query with the cross-encoder, keeps the top `k_eval = 10` |
| `grade` | Asks `qwen3:8b` (JSON schema `{reason, verdict}`) whether the top `k_context = 5` passages are enough to answer the **original** question. A parse failure counts as "insufficient" (D27, D30) |
| `rewrite` | One-line replacement query written from the grader's reason and all earlier queries, so it does not repeat itself (D28) |
| `generate` | Answers from the top 5 passages with `[P1]`…`[P5]` labels, or replies `INSUFFICIENT_EVIDENCE` |
| `verify` | Splits the answer into sentences and checks each against its cited passages (next section) |
| `abstain` | Returns `INSUFFICIENT_EVIDENCE: <reason>` where the reason is the grader's own explanation of what is missing |

Rules that are easy to get wrong, and where they live:

- **The retry limit is enforced in exactly one place**, `route_after_grade`: `attempts ≤ max_retries` rewrites, otherwise abstains. With `max_retries = 2` a question gets at most three retrievals. A run across the full dev sample logged no query above that limit (M4 gate).
- **The grader and the generator always see the user's original question.** Only retrieval and reranking use the rewritten query, so a rewrite can widen the search but cannot change what is being asked.
- **Every node appends one entry to `trace`** (`node`, `ms`, and what it decided). That list is the per-query log in the results files, and it is exactly what the web UI streams.

A question's trace, with the number of steps measured on the full index ([`m10_stream_latency.json`](results/m10_stream_latency.json)):

| Case | Trace | Steps |
|---|---|---|
| answered first try | retrieve → rerank → grade → generate → verify | 5 |
| rescued by a rewrite | retrieve → rerank → grade → rewrite → retrieve → rerank → grade → generate → verify | 9 |
| abstained after 2 retries | (retrieve → rerank → grade → rewrite) ×2, then retrieve → rerank → grade → abstain | 12 |

### Retrieval

| Stage | Detail | Decision |
|---|---|---|
| Dense | Qdrant, cosine, `nomic-embed-text`, top 50 | D15 |
| Sparse | `bm25s` (k1 1.5, b 0.75, English stemming and stopwords), top 50 | D21 |
| Fusion | Reciprocal Rank Fusion, `score(d) = Σ 1 / (60 + rank(d))` over both rankings; ties break on `(paper_id, chunk_idx)` so the order is deterministic | D22 |
| Rerank | `BAAI/bge-reranker-v2-m3`, fp16 on CUDA, `max_length` 512, batch 16, over the fused 50; the top 10 are scored, the generator sees the top 5 | D23 |

RRF is rank-based, so dense cosine scores and BM25 scores never need to be put on a common scale, and one retriever cannot dominate. On the same 303 questions, hybrid retrieval lifts R@5 from 0.868 (dense) to 0.908 and the cross-encoder to 0.944; the full ablation, with per-query latency, is in [`results/m3_ablation.md`](results/m3_ablation.md) (D24). The reranker is the slowest stage on a CPU (39.7 s against 1.4 s per query on the GPU, D29), which is why the Docker CPU image works but is not the recommended way to run it.

### Generation, citations and the grounding check

- **The model cites labels; code resolves them.** The generator sees passages as `[P1]`…`[P5]` and ends each sentence with the label of the passage that supports it. Code, not the model, turns a label into `(paper, section, page)` from the chunk's stored metadata, so a citation can only point at a passage that was actually retrieved. Labels are `P`-prefixed because the papers' own bibliography markers (`[21]`) collided with plain numbers (D31, D34).
- **The grounding check is joint, per sentence.** For each sentence, one LLM call asks whether its cited passages *together* support everything it says (per-passage checks let one passage carry a second, unsupported claim). A sentence that passes keeps its citations. A sentence that fails, or has no citation, is tried against each other retrieved passage alone and re-attributed to the first that supports it; otherwise it is **removed**. If no sentence survives, the answer becomes an abstention (D32, D35).
- **Output form:** `... Adam with a learning rate of 3e-4 [2406.01234v2 §4 p.6].` and, in the JSON response, a deduplicated `citations` list of paper, section, section title and page.
- **What this does and does not prove.** The citation-validity figure in the results is the pipeline's own check (0.97+). When I read 10 cited answers by hand, 7 had valid citations, so it is an upper bound (D35, [Known limitations](#known-limitations)).

### Serving: HTTP API, SSE and the web UI

| Route | Purpose |
|---|---|
| `GET /health` | Liveness: the process is up (answers even while Ollama is down) |
| `GET /ready` | Readiness: `200 {"status": "ready"}`, or `503` with the reasons (Ollama unreachable, a model not pulled). The index is checked once at startup: the app refuses to start without it and prints how to build it |
| `POST /query` | One question → one JSON answer (`answer`, `abstained`, `abstain_reason`, `citations`, `retries`). Queued behind a running query |
| `POST /query/stream` | The same pipeline as Server-Sent Events: `step` events (one per graph node), then `final` (the answer plus `total_ms` and the sentences the grounding check removed) or `error`. `429` if busy |
| `GET /` | The web UI |
| `GET /ui/ask`, `GET /ui/stream` | The UI's two GET routes (the htmx SSE extension can only open `GET` event streams); `/ui/stream` renders each event as an HTML fragment and always ends with `done` |
| `/static/*` | Vendored htmx, its SSE extension, KaTeX and CSS: no CDN, no npm, no build step |

```mermaid
sequenceDiagram
    actor U as Browser
    participant A as FastAPI app
    participant G as LangGraph run
    participant O as Ollama
    U->>A: GET /ui/ask?question=...
    A-->>U: HTML fragment that opens an EventSource
    U->>A: GET /ui/stream?question=... (SSE)
    A->>G: graph.stream(question, stream_mode="values")
    loop each node: retrieve, rerank, grade, rewrite, generate, verify
        G->>O: embed / chat / classify (the LLM nodes)
        O-->>G: result
        G-->>A: new trace entry
        A-->>U: event: step (node, ms, what it decided)
    end
    A-->>U: event: final (answer, citation chips, removed claims)
    A-->>U: event: done (the page closes the EventSource)
```

- **One query at a time (D37).** One GPU serves both the LLM and the reranker, and embedded Qdrant is single-process, so concurrency would only queue on the GPU. A second `/query/stream` or UI request gets a clear *busy* response; `/query` waits for the lock.
- **The UI streams the real trace.** The corrective loop (including rewrites and retries), citation chips linking to the arXiv PDF at the cited page, abstention reasons, and struck-through removed claims are rendered from the same events as the API (D43). LaTeX in answers is typeset with vendored KaTeX.
- **`GET /ui/stream` starts a GPU run**, so `/ui/*` rejects `Sec-Fetch-Site: cross-site` requests: another web page cannot trigger a run in your browser. There is no authentication, which is why the Docker port is bound to loopback.

### Deployment: Docker

The Docker setup (M11) is two containers, one volume and one bind mount. The image contains the code and the Python environment only; the corpus, the index and the model weights never enter an image layer.

```mermaid
flowchart LR
    subgraph host["Host: Windows, macOS or Linux with Docker, optional NVIDIA GPU"]
        browser["Browser or curl<br/>127.0.0.1:8000"]
        data[("./data (bind mount)<br/>pdfs · hf · index/qdrant · hf_cache")]
    end
    subgraph compose["docker compose project: halo"]
        subgraph appc["app container: halo:cpu or halo:cu128, non-root"]
            ep["entrypoint.sh<br/>scripts/pull_models.py"] --> uv["uvicorn halo.api.app:app<br/>port 8000"]
        end
        subgraph olc["ollama container"]
            ollama["ollama/ollama<br/>port 11434, not published"]
            vol[("named volume: ollama<br/>model weights")]
        end
    end
    browser -- "127.0.0.1:8000" --> uv
    uv -- "HALO_OLLAMA_URL=http://ollama:11434" --> ollama
    ep -- "pull qwen3:8b and nomic-embed-text if missing" --> ollama
    data -- "/app/data" --> appc
    ollama --- vol
```

- **Two image variants from one Dockerfile.** `halo:cpu` (default) and `halo:cu128` (`--build-arg TORCH=cu128`, selected by `docker-compose.gpu.yml`). `uv.lock` already resolves Linux to CPU wheels; the GPU variant reinstalls `torch` from the CUDA 12.8 index. The GPU override also reserves the NVIDIA device for Ollama and the app.
- **Start-up order is enforced.** `app` waits for Ollama's healthcheck; its entrypoint then pulls any missing Ollama model and the reranker's weights (so the first *query* never stalls on a download), skipping anything already present, so a restart works offline; then `uvicorn` starts and refuses to come up if the index collection is missing. The compose healthcheck polls `/ready`.
- **Configuration by environment, not by editing TOML.** `HALO_OLLAMA_URL`, `HALO_RERANK_DEVICE` (`auto` in the image: GPU when present) and `HALO_COLLECTION` override three config values; every other tunable stays in [`config/default.toml`](config/default.toml), so results files keep describing the pipeline (D44).
- **Loopback only.** Port 8000 is published on `127.0.0.1`, Ollama's port is not published at all (so it cannot clash with a host Ollama), and the app runs as a non-root user.

### Evaluation harness and CI

```mermaid
flowchart LR
    sp["splits/*.json<br/>one fixed seed, SHA-256 headers,<br/>byte-reproducible"] --> run["eval.runners.run<br/>any pipeline on any split"]
    idx[("Qdrant index")] --> run
    run --> res["results/*.json<br/>config + git commit + dirty flag + judge<br/>metrics overall and by type and modality"]
    res --> rd["eval.report.readme"] --> rm["README results tables"]
    res --> ci["eval.runners.ci check"]
    subgraph gh["GitHub Actions on every PR"]
        l["ruff"] --> t["pytest"] --> ci
    end
```

- **Splits are fixed and never re-rolled.** `held_out` (20 source papers, never indexed), `abstention_set` (all 152 questions of those papers; the correct behavior is to abstain), `dev_slice` (~100 papers for iteration), `dev_sample` (303 questions, selected at paper level) and `full` (2,891 answerable questions, run only at milestone completion). One seed, committed files, SHA-256 of the sources in each header, regenerated byte-identically (D4–D9).
- **Metrics.** Retrieval: R@5, R@10, MRR and nDCG@10 against the single gold section per question (with one relevant section, R@k is hit@k and MRR is the most informative number). Answer: Correct (LLM judge against the reference) and Faithful (is the answer supported by its context). Abstention: the share of `abstention_set` refused, and the false-abstention rate on answerable questions. Citations: validity and coverage. Everything is reported overall and by question type and modality, never by the 8-cell cross (cells too small). Definitions: D16, D17.
- **Every run writes one results JSON** with the full config snapshot, the git commit and whether the tree was dirty, the judge model, timestamps and per-query records. The README tables are generated from those files, so a number cannot be edited into the README by hand.
- **The judge was calibrated.** 50 blind human labels against two judges, Cohen's κ per verdict kind (M7, D39); the result and its direction of bias are in [Known limitations](#known-limitations).
- **CI regression gate (M8, D40).** On a hosted runner there is no index and no Ollama, so CI does not re-run retrieval. It checks a committed results file instead (`results/ci_retrieval_dev_sample.json`, produced locally by `eval.runners.ci run`): the file fails the gate if it was made from a dirty tree, from a commit that is not an ancestor of `HEAD`, or before a watched path (`halo/`, `config/`, `splits/`, `eval/`, `pyproject.toml`, `uv.lock`) changed; if its summary does not match its per-query records; or if R@5 or MRR dropped more than 0.005 below the committed baseline. A deliberately degraded config (reranking off) failed the gate on a real PR ([`results/m8_gate.md`](results/m8_gate.md)).

### Design invariants

- Evaluation before optimization: a feature without a measured before/after is not done, and every README number comes from `results/`.
- The retry limit lives in one function; the grader and generator always see the original question.
- Citations are resolved from stored chunk metadata by code, never from model text.
- Deterministic where it can be: temperature 0 and a fixed seed for the LLM, a deterministic RRF tie-break, byte-reproducible splits, idempotent ingestion.
- Config over code: every tunable (k values, RRF constant, retry limit, model names, prompts and their versions, thresholds) is in [`config/default.toml`](config/default.toml). Environment variables only carry facts that differ per deployment.
- Every non-obvious choice has an entry in [`DECISIONS.md`](DECISIONS.md) (D1–D44) with the alternatives and the metric that justified it.

## Benchmark and data splits

[Vectara Open RAG Bench](https://huggingface.co/datasets/vectara/open_ragbench) ([GitHub](https://github.com/vectara/open-rag-bench)), arXiv subset, official release:

- 1,000 papers: 396 papers with questions + 604 distractors
- 3,045 questions, labeled extractive/abstractive and by modality (text, text+image, text+table, text+table+image)
- Section-level relevance labels: exactly one relevant section per question

The MVP parses text only, so **text-modality questions are the primary metric**; image/table questions are still evaluated and reported separately so the gap is visible. Dataset formats as actually inspected are documented in [`DATA.md`](DATA.md); design choices and their justifying numbers in [`DECISIONS.md`](DECISIONS.md).

| Split | Contents | Used for |
|---|---|---|
| `held_out` | 20 source papers, never indexed at any scale | defines the abstention test |
| `abstention_set` | all 152 questions of the held-out papers | abstention rate (correct behavior: refuse) |
| `dev_slice` | ~100 papers: 40 source papers + 60 distractors from the same arXiv categories | every iteration, M1–M5 |
| `dev_sample` | 303 questions of the 40 dev source papers | tuning and the progression table |
| `full` | 2,891 answerable questions | milestone completion runs only |

## Stack

| Layer | Choice |
|---|---|
| Language, packaging | Python 3.12, [uv](https://docs.astral.sh/uv/) |
| Orchestration | LangGraph (the corrective loop as an explicit state graph) |
| Generation, grading, rewriting, citation check | Ollama, `qwen3:8b`: the best model that fits a 6 GB RTX 4050 at Q4 (D10); name is config, not code |
| Embeddings | `nomic-embed-text` via Ollama |
| Vector store | Qdrant, embedded (local) mode; no server |
| Sparse retrieval | `bm25s` |
| Reranker | `BAAI/bge-reranker-v2-m3` cross-encoder via sentence-transformers |
| PDF parsing | PyMuPDF, text only |
| Serving | FastAPI, uvicorn, htmx + Jinja2, Server-Sent Events |
| Packaging for deployment | Docker, Docker Compose (CPU and CUDA variants) |
| Quality | pytest, ruff, GitHub Actions |

Fully local: nothing leaves the machine except the one-time downloads (arXiv, Hugging Face, Ollama's model registry).

## Quickstart

### Docker (recommended)

Needs [Docker](https://docs.docker.com/get-docker/) with Compose v2. For the GPU variant: an NVIDIA GPU and either Docker Desktop with WSL2 or the NVIDIA Container Toolkit. Disk, as measured on the machine in [Docker results](#docker-deployment-m11): the `ollama/ollama` image is 8.5 GB and its models another ~5.5 GB, the PDFs and index in `data/` ~6 GB, and the HALO image 2.2 GB (CPU) or 8.7 GB (CUDA).

```bash
git clone https://github.com/lunatictiol/halo && cd halo

# 1. Build the image once.
docker compose build                                                      # CPU variant
docker compose -f docker-compose.yml -f docker-compose.gpu.yml build      # NVIDIA GPU variant

# 2. Build the index, once (the first command also pulls the models, see below).
docker compose run --rm app python scripts/download_data.py        # HF metadata + corpus + 1,000 arXiv PDFs (~1 h, resumable)
docker compose run --rm app python scripts/ingest.py --split full  # chunk + embed the 980 indexable papers (~1-2 h on a GPU)

# 3. Serve.
docker compose up -d                                               # web UI at http://127.0.0.1:8000/
```

With the GPU variant, pass the same `-f docker-compose.yml -f docker-compose.gpu.yml` to every `docker compose` command (or export Compose's `COMPOSE_FILE` variable). Plain commands use the CPU image, which works but reranks ~30× slower.

What happens on first start:

- The `ollama` container starts and passes its healthcheck; the `app` entrypoint then pulls `qwen3:8b` (~5.2 GB) and `nomic-embed-text` (~0.3 GB) into the `ollama` volume, and the reranker's weights (~2 GB) into `data/hf_cache`. Later starts skip all of it, offline.
- If you run `up` without an index, the app exits immediately with `index collection 'full' not found: build it first` instead of failing on the first question.
- `docker compose ps` shows `app` as *healthy* once `/ready` answers; `curl http://127.0.0.1:8000/ready` shows why if it does not.

Day-to-day:

```bash
docker compose logs -f app          # follow the pipeline
docker compose stop app             # REQUIRED before re-ingesting: embedded Qdrant allows one process
docker compose down                 # stop everything; models and index are kept
docker compose down -v              # also delete the Ollama model volume (it will be re-pulled)
```

Faster try-out on the ~100-paper dev slice (still needs `download_data.py` to finish, which fetches all PDFs):

```bash
docker compose run --rm app python scripts/ingest.py --split dev_slice
HALO_COLLECTION=dev_slice docker compose up -d
```

Keep the data somewhere else with `HALO_DATA=/path/to/data docker compose ...`. On a Linux host, `./data` must be writable by the container user (uid 1000 by default); otherwise set `HALO_UID` and `HALO_GID` to its owner.

### Local (uv)

Needs [uv](https://docs.astral.sh/uv/) and [Ollama](https://ollama.com/). A CUDA GPU is optional: on a CPU-only machine set `[rerank] device = "auto"` in `config/default.toml` (or `HALO_RERANK_DEVICE=auto`); reranking is ~30× slower on CPU.

```bash
git clone https://github.com/lunatictiol/halo && cd halo
uv sync
ollama pull qwen3:8b && ollama pull nomic-embed-text

uv run python scripts/download_data.py          # HF metadata + parsed corpus + 1,000 arXiv PDFs (~1 h, resumable)

uv run python -m halo.cli "What datasets are used to evaluate the proposed method?"
uv run uvicorn halo.api.app:app                 # web UI at http://127.0.0.1:8000/, POST /query, POST /query/stream, GET /health, GET /ready
```

For a faster try-out, `scripts/ingest.py --split dev_slice` indexes the ~100-paper dev slice and `python -m halo.cli --collection dev_slice "..."` queries it (`HALO_COLLECTION=dev_slice` serves it from the API).

### Asking questions

```bash
# Web UI
open http://127.0.0.1:8000/

# JSON API
curl -s http://127.0.0.1:8000/query -H 'content-type: application/json' \
     -d '{"question": "What optimizer does the paper use?"}'

# Streaming: one `step` event per graph node, then `final`
curl -N http://127.0.0.1:8000/query/stream -H 'content-type: application/json' \
     -d '{"question": "What optimizer does the paper use?"}'

# Inside the Docker stack, without the server
docker compose run --rm app python -m halo.cli "What optimizer does the paper use?"
```

`POST /query` returns:

```json
{"answer": "... [2406.01234v2 §4 p.6].", "abstained": false, "abstain_reason": null,
 "citations": [{"paper_id": "2406.01234v2", "section_id": 4, "section_title": "Experiments", "page": 6}],
 "retries": 0}
```

An abstention has `"abstained": true`, an answer that starts with `INSUFFICIENT_EVIDENCE:` and an `abstain_reason`. A question must be non-empty and at most 1,000 characters (the longest benchmark question is 197).

### Troubleshooting

| Symptom | Cause and fix |
|---|---|
| App exits with `index collection 'full' not found` | The index step has not run, or you ingested another split: run `ingest.py --split full`, or serve the one you built with `HALO_COLLECTION` |
| `/ready` returns 503 `ollama unreachable` or `model ... not pulled` | First start is still pulling; watch `docker compose logs -f app` and `docker compose logs ollama` |
| `429 busy` / "Busy" in the UI | One query at a time by design (D37); retry when the running one finishes |
| Every query takes minutes | Probably the CPU image on a machine with a GPU: use the GPU variant, or the CPU reranker costs ~40 s per query |
| Out of GPU memory | `[llm] num_gpu = 22` is tuned for 6 GB; lower it on smaller GPUs, raise it on larger ones |
| `PermissionError` under `./data` (Linux) | The container user cannot write the bind mount: set `HALO_UID` and `HALO_GID` to the owner of `./data` |
| `database is locked` / Qdrant lock error during ingest | `app` is still running: `docker compose stop app` first |
| Port 11434 already used | Not a Docker problem: the compose Ollama publishes no port, so a host Ollama does not clash |

### Why the full corpus scores lower

From [`results/m6_report.md`](results/m6_report.md), each comparison changes one thing at a time:

- **The bigger index costs little.** On the same 303 `dev_sample` questions, moving from the 100-paper dev index to the 980-paper index lowers R@5 from 0.937 to 0.927 and Correct from 0.901 to 0.898. Ten times more distractors barely hurt retrieval.
- **Most of the drop comes from the questions.** Inside the single full-index run, `dev_sample` questions score 0.894 Correct and the other 2,590 questions score 0.835. Retrieval is almost the same (R@5 0.927 vs 0.915), but those questions are answered less well when answered (0.934 vs 0.892), abstained on more often (0.043 vs 0.063), and include harder text-image questions (Correct 0.806 vs 0.699). Every prompt and threshold was tuned on `dev_sample`, so it is an optimistic estimate; **the `full` numbers are the honest ones.** Of the 427 wrong answers among the other questions, 216 had the gold section in the top-5 (a generation or judging miss), 164 were refusals, and only 47 were retrieval misses.
- **Abstention weakens as the corpus grows.** On the same 152 `abstention_set` questions, HALO answered 34 with the full index against 21 with the dev index. For 17 of the 34, the top passage came from an official distractor: more papers means more passages close enough to a question that the grader judges them sufficient (24 of the 34 were graded sufficient on the first attempt). Some of these may genuinely be answered by another paper; they were not hand-checked.

### Chunking benchmark (M9)

Three chunking strategies on the 100-paper dev index, same retrieval pipeline (`hybrid_rerank`), `dev_sample` (n = 303). From [`results/m9_chunking.md`](results/m9_chunking.md):

| Strategy | Chunks | R@5 | R@10 | MRR | nDCG@10 | Ingest cost |
|---|---|---|---|---|---|---|
| **Section-aware (shipped)**: 300-word windows that never cross a section | 6,740 | 0.944 | 0.970 | 0.830 | 0.865 | 3 min |
| Fixed-size: the same windows, ignoring sections | 5,406 | 0.766 | 0.815 | 0.642 | 0.684 | 2 min |
| Section-aware + contextual enrichment: 1–2 LLM lines situating each chunk in its paper | 6,740 | 0.941 | 0.980 | 0.837 | 0.872 | 188 min (3.2 GPU-h of `gemma3`) |

```mermaid
xychart-beta
    title "MRR by chunking strategy (hybrid_rerank, dev_sample)"
    x-axis [section, fixed, enriched]
    y-axis "MRR" 0.6 --> 0.9
    bar [0.830, 0.642, 0.837]
```

- **Section boundaries matter.** Fixed-size windows lose 0.18 R@5. Part of that is structural: 46 gold sections are too short to be the majority of any window, so they can never be hit. But on the 257 questions fixed-size *can* answer, it still trails (R@5 0.903 vs 0.957, MRR 0.757 vs 0.856).
- **Contextual enrichment is a tie, so it is not shipped.** It improves R@10 and MRR slightly but loses 0.003 R@5. Per question it moved the gold section up for 36 and down for 35. Those differences are within run-to-run noise (re-embedding the same chunks moved dense R@5 by 0.003). Rebuilding the full index would take about 29 GPU-hours. It was not run end-to-end, because retrieval showed no gain and most wrong answers are generation misses (D42).

### Streaming API and web UI (M10)

`POST /query/stream` runs the same pipeline as `/query` and streams it as Server-Sent Events: one `step` event per graph node (`retrieve`, `rerank`, `grade`, `rewrite`, `generate`, `verify`, `abstain`) with its time and what it decided, then a `final` event with the `/query` answer plus `total_ms` and the sentences the grounding check removed. A second request while one is running gets `429 busy`. The page at `/` (htmx + Jinja2, vendored, no build step) shows the same stream live: the corrective loop with its rewrites, citation chips linking to the arXiv PDF at the cited page, abstention reasons, and removed claims struck through.

|---|---|---|---|

| rescued by a rewrite | 0.76 s | 48.6 s | 9 | 1 | 40.5 s |
| abstention (2 retries) | 1.59 s | 270.6 s | 12 | 2 | 37.7 s |

All three behaved as in M10 (0, 1 and 2 retries, and the last one abstained), and `GET /` returned the page with its question form.

**Read the latency with care.** This is one run, and the abstention row is an outlier: two earlier clean runs of the same script (not kept, because the script overwrites its file) gave abstention totals of 52.2 s and 50.3 s, rescued 48.3 s and 54.1 s, direct 23.0 s and 22.5 s, and cold starts of 43.6 s and 67.1 s. So the direct question matches native, the rescued one is roughly 20-35% slower, and the abstention total ranges from about 1.3× to 7× the native figure. After the run the 6 GB card showed 5,614 MiB in use while idle. When VRAM is that tight, the LLM and the reranker can spill into shared memory, the mechanism D29 recorded on the native setup. That is consistent with the spread, but I did not show it to be the cause. Treat Docker latency on a 6 GB card as unreliable, and on a larger GPU as unmeasured.

## Known limitations

- **Text only.** Figures and tables are not parsed, so questions whose answer lives in an image or a table are answered from surrounding prose or not at all. The modality rows above show the gap.
- **The judge agrees only moderately with a human.** `qwen3:8b` both generates and judges. Against 50 blind labels of mine it scores Cohen's κ 0.48 on faithfulness and 0.56 on correctness ([`results/m7_judge_calibration.md`](results/m7_judge_calibration.md)). A judge from another family, `llama3.1:8b`, did worse (κ 0.12 and 0.48), so qwen stays the judge and no number above moved. The errors have a direction: of the sampled answers qwen called *supported*, 4 of 17 were unsupported to me, so **Faithful is overstated**; of those it called *incorrect*, 4 of 10 were correct to me, so **Correct is somewhat understated**. The sample oversamples negatives, so these show direction, not corrected rates (D39).
- **Citation validity is self-checked and overstated.** The "Cite valid" column is the pipeline's own grounding check (0.97+). When I reviewed 10 cited answers by hand, 7 had valid citations (M5, [`DECISIONS.md`](DECISIONS.md) D35): the checker passes overreaching inferences and two-part sentences where only one part is supported.
- **Abstention is tested on a proxy.** `abstention_set` questions come from papers that are never indexed. Another indexed paper can occasionally answer one, so a few "wrong" answers there may be right.
- **Small local model.** An 8B model at Q4 on a 6 GB GPU, with tens of seconds per question (median in the table). A hosted model is a config change (`[models] llm`) that has not been measured.
- **One query at a time.** One local GPU and embedded single-process Qdrant: `/query` queues requests, while `/query/stream` and the web UI answer a second concurrent request with `429 busy`.
- **Tuned on the dev sample.** All prompts and thresholds were chosen on `dev_sample`, which scores higher than the rest of the corpus (see above). Expect the `full` numbers, not the dev ones.
- **Abstention depends on corpus size.** More distractors give the grader more near-miss passages to accept; abstention fell from 0.862 to 0.776 when the index grew tenfold.
- **Setup takes a while.** The index is not shipped (it contains the papers' text), so the quickstart downloads 1,000 PDFs and builds the index locally. Docker does not change that; it makes the setup reproducible, not shorter.
- **One gold section per question.** Open RAG Bench labels exactly one relevant section, so a correct passage from another section counts as a retrieval miss.
- **Docker: what was and was not exercised (M11).** Verified on one machine (Windows 11, Docker Desktop with WSL2, one RTX 4050 laptop GPU): the GPU image builds and serves the full index, the CPU image builds, the index step (`ingest.py --split dev_slice`) runs in a container and produces the same 6,740 chunks as the native run, and `download_data.py` was run in a container for 90 s only (metadata and corpus files landed in the mounted volume; the one-hour PDF phase was not run there). **Not exercised:** the CPU image answering a query, a Linux host or the NVIDIA Container Toolkit (the `HALO_UID`/`HALO_GID` mapping is untested), and macOS.
- **Docker: container latency is slower than native on multi-attempt questions and varies a lot.** In the saved run the abstention question took 270.6 s against 37.7 s native, and earlier unsaved runs sat near 50 s (see the [Docker results](#docker-deployment-m11)). A nearly full 6 GB card is a candidate cause, not a finding; I did not investigate further. Latency is one saved run plus two unsaved ones, not a distribution.
- **No authentication and no `Host` check.** The Docker port is loopback-only, which is the protection. A DNS-rebinding page could still reach a loopback server from the user's own browser; `/ui/*` rejects cross-site `Sec-Fetch-Site` requests, but the JSON endpoints do not check the `Host` header (D43, D44). Do not publish the port to a network.
- **Unpinned base images.** `ollama/ollama:latest` is not pinned, and the CUDA image pins `torch==2.11.0` by hand (the CPU image follows `uv.lock`); a future Ollama or torch release can change behavior without a code change.
